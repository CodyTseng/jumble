# Error diagnostics

The error page displays and copies the JavaScript stack, React component stack,
version, Git commit, timestamp, path, and browser/runtime details. A screenshot
may omit frames below the scroll area; prefer the full copied report.

## Build artifacts

Web and Electron builds generate external source maps with embedded
source content. Renderer maps are in `dist/`; Electron main/preload maps are in
`dist-electron/`. The JS bundles include `sourceMappingURL` comments so DevTools
can discover the maps automatically. Deploy the maps alongside the web bundles;
Electron packages include them too. These maps publicly expose the original
source code, which is intentional for this open-source project.

Web CI and the standard Electron CI/release jobs archive matching JavaScript
bundles and maps as `source-maps-*` artifacts,
labelled by commit and platform, for 90 days. Release publishing downloads only
`jumble-*` installer artifacts, so diagnostic artifacts are not attached to
GitHub Releases. Download artifacts before they expire when longer retention is
needed. Artifact access follows the repository's GitHub Actions permissions.

Flatpak builds also generate maps inside their build environment, but do not
currently archive them separately.

For web deployments outside these workflows, archive the JS and maps **from the
actual deployed build** before deployment. Rebuilding the same commit with other
dependencies, environment variables, or tool versions can produce different
bundles and mappings. Keep the `.map` files in the web deployment so DevTools
can fetch them when debugging. They are not part of normal page loading.

## Locate an error

1. Match the report's commit, runtime, and bundle filename to its build artifact.
2. Find the stack frame's generated JS filename, line, and column. Preserve these
   even if the function name is shortened by minification.
3. Open Chrome DevTools with JavaScript source maps enabled to resolve the
   deployed bundles automatically. For an older deployment, load the archived
   JS and use **Add source map** to load its corresponding `.map` file (serve the
   artifact locally if needed). DevTools can then map the generated location to
   the original TypeScript/TSX.
4. Use the React component stack and surrounding frames to understand the path
   that led to the error. A throwing line alone may not explain the bad data.

The error page lazy-loads the mapping code after a crash and fetches the matching
`.js.map` files from the application's own origin. It resolves JavaScript and
React component stack locations where available, showing the resolved error
stack near the top for screenshots. Copied reports include the resolved stack
and the original JavaScript stack. Mapping does not mutate `Error.stack` itself.

Map downloads time out after eight seconds. Missing, invalid, offline, external,
or unmapped frames retain their original locations. The page and copy/reload
controls remain usable while resolution runs. Older releases built without maps
cannot be reliably symbolicated using maps generated by a new build.
